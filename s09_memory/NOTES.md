# s09 · Memory —— 学习笔记

> 本章教程：[README.md](./README.md) · 参考实现：`../learn-claude-code-main/s09_memory/code.py`

> **格言**：记住该记的，忘掉该忘的 —— 三个子系统：筛选、提取、整理

## 学习目标

- 实现记忆的三个子系统：selection（选择）、extraction（提取）、consolidation（整理）
- 一条记忆一个文件，按需召回，而不是全部塞进 system prompt
- 让重要信息跨会话保留下来

## 本章要回答的问题

1. 什么信息值得跨会话保存？什么应该丢弃？
2. 召回时如何"先选目录、再加载正文"？
3. 记忆冲突或过期时如何整理？

### 1. 先理解：模型为什么会“忘记”？

调用模型时，程序会把 `messages` 等内容发给模型，模型根据这一次收到的内容回答问题。以前聊过的信息，如果这次没有再发给它，它就无法仅凭上一次的 API 调用想起来。

同一个会话里，程序通常不断往 `messages` 追加消息，所以模型看起来一直记得。退出程序、重新开始一个会话后，如果没有重新加载旧信息，这份记忆就断了。

s09 要做的事情可以理解为：**给 Agent 配一本能保存在磁盘上的笔记本。下次遇到相关问题时，程序先翻笔记，再把有用的内容交给模型。**

这里的“记忆”没有修改模型参数，而是程序在模型外面保存和读取文件。

### 2. 和刚写过的 s08 有什么区别？

s08 关心的是：“这一次任务的聊天太长了，怎么腾出上下文空间，让任务还能继续？”你实现的历史外存、工具结果压缩和模型摘要，都是围绕当前会话的预算展开的。

s09 关心的是：“这次聊天里，有什么信息值得下次任务继续使用？”例如你一直使用什么语言、项目使用什么数据库、你对协作方式有什么长期要求。

举个例子：一次排错产生了 500 行日志。

- s08 可以把日志移到外部，在当前上下文里留下路径，方便继续排错。
- s09 可以留下“这个项目的日志目录是哪个”这样的稳定线索。500 行原始日志通常不需要成为长期记忆。

所以，保存了完整聊天记录，不等于已经做好了长期记忆。长期记忆还需要挑选信息，并在合适的时候取回来。

### 3. 先跟着一条信息走完全过程

假设第一次会话里，用户说：“以后讲解代码都用中文。”

1. Agent 先正常完成当前回答。
2. 回合结束后，提取步骤检查对话，发现这是一条以后也适用的偏好。
3. 程序检查候选信息，确认可以长期保存，再写入 `.memory/` 下的一个文件。
4. 程序更新 `MEMORY.md` 索引，让目录里能找到这条偏好。
5. 用户退出程序。磁盘上的文件仍然存在。
6. 下次启动，用户让 Agent 解释一个函数。程序先查看记忆目录，选出这条相关偏好，读取它的正文。
7. 程序把这条背景信息放进本次模型请求，模型就能据此用中文讲解。

**跨会话记住信息的关键，是磁盘保存 + 下次请求重新加载。** 只写文件但不召回，模型仍然用不上；只保存在 `messages` 中，开启新会话后又会丢失。

### 4. 存储：为什么要有“目录”和“正文”？

可以把 `.memory/` 想成一个笔记文件夹：每条记忆单独一页，`MEMORY.md` 是这些笔记的目录。

```text
.memory/
├── MEMORY.md                  # 索引：每条记忆的简短介绍和位置
├── user-language.md           # 正文：用户的语言偏好
└── project-database.md         # 正文：项目的数据库信息
```

每个记忆文件开头的 `---` 之间是元数据，也就是供程序识别的标签；后面才是正文：

```markdown
---
name: user-language
description: 用户希望用中文讲解代码
type: user
---

用户希望后续代码讲解使用中文，代码标识符继续使用英文。
```

- `name`：这条记忆叫什么，用来标识记录。
- `description`：一句话简介，帮助选择阶段判断是否相关。
- `type`：记忆属于哪一类。
- 正文：真正需要交给模型使用的详细信息。

课程把类型分成四类：`user` 保存长期偏好；`feedback` 保存以后仍适用的工作反馈；`project` 保存稳定的项目事实；`reference` 保存外部资料的位置或查找线索。

写入记忆后，`rebuild_memory_index()` 会根据记忆文件重新生成目录。这样新增或修改正文后，索引也能跟着更新。

### 5. 召回：先看目录，再翻需要的几页

假设已经存了 100 条记忆，用户现在问：“帮我解释这个 Python 函数。”这时数据库迁移记录、部署问题等记忆可能完全用不上。

如果每次都把 100 条正文放进 system prompt，就会花费更多 token，也会让模型读到很多无关信息。因此，课程把读取分成两步：

1. **选择**：`select_relevant_memories()` 根据最近的用户消息和记忆目录，让模型选出相关记录，最多五条。
2. **加载**：`load_memories()` 再读取被选中的文件正文，并限制加载内容的总长度。

这里让选择模型返回 `[0, 2]`，意思是“选择当前目录里编号为 0 和 2 的记录”。这些数字是目录位置，不是相关性分数。返回 `[]` 表示没有合适的记忆，本次可以不加载。

如果选择模型调用失败，或者返回的内容无法解析成 JSON，程序退回关键词匹配，让召回还有一个备用办法。

最后，`build_system(relevant_memories)` 把召回的内容组装进 system prompt。模型能使用这些记忆，是因为本次请求里包含了它们。

**旧记忆只提供背景，当前用户请求优先。** 例如记忆里写“平时用中文”，用户这次明确说“请用英文回答”，就应当用英文。放进 system prompt 的记忆，也需要明确标注这个使用边界。

### 6. 提取：这句话下次还应该生效吗？

`extract_memories()` 在本轮回答完成后，从对话里找出值得长期保存的信息。这里的“回合结束”指 Agent 已经完成本轮工作，不是每执行完一个工具就立刻提取。

提取模型给出的只是候选。程序还要用 `should_store_memory()` 检查，不能让模型说存什么就直接存什么。

最重要的判断是作用范围 `scope`：

- `persistent`：跨会话仍有用，可以进入后续的保存检查。例如“以后都用中文解释”。
- `current_task`：只适用于当前任务。例如“这次只分析，不要修改文件”。

候选还需要字段完整，并通过临时性和重复检查。即使模型把一条临时要求标成 `persistent`，程序仍需要拦截明显只针对“本次会话”或“当前任务”的内容。

为什么要这么谨慎？如果把“这次不要创建文件”长期保存，下次用户明确要求创建文件时，Agent 可能还会受到旧要求干扰。**错误的记忆会影响以后的任务，所以写入前需要筛选。**

这一步也不等于每轮都必须存一条。普通问答、临时路径或一次性的执行结果，没有长期价值就可以不存。

### 7. 整理：笔记多了，要去重和更新

长期使用后，可能存下多条意思相近的记忆，比如“解释时用中文”和“代码讲解使用中文”；也可能出现旧事实，例如项目以前用 MySQL，后来迁移到了 PostgreSQL。

`consolidate_memories()` 的目标是让模型生成一份整理后的记录列表，减少重复，处理需要更新的内容。课程为了简化实现，达到 10 条记忆时触发整理。这个数字是教学实现的阈值，不是所有系统都必须遵守的规则。

整理会改写已有文件，因此需要保护原来的数据：

1. 先拿到并解析、校验整理结果。
2. 在替换前保存旧记忆文件的快照。
3. 用整理后的记录替换旧文件，重建索引。
4. 如果删除或写入失败，就用快照恢复旧文件，再重建索引。

这里的快照在示例中是程序内存里的旧文件内容，能帮助处理被捕获的异常。它并不等于已经解决了进程突然退出、断电或多个进程同时写入的问题。

另外，模型也不一定能凭两条互相冲突的记录判断哪条更新。真实系统通常还需要时间、来源或进一步确认，帮助判断事实是否过期。

### 8. 把它接回 Agent Loop

先记住两个时机：**用户开始新一轮请求时召回，本轮真正结束后提取。**

按照教程展示的流程，可以这样读：

1. 收到用户请求，将消息加入对话。
2. 查找相关记忆，加载正文，组装本次使用的 system prompt。
3. 进入原来的 Agent Loop：调用模型，有工具调用就执行工具、追加结果，再继续调用模型。
4. 模型不再请求工具时，检查 `Stop` hook。
5. 如果 hook 要求继续工作，把要求加入消息，继续循环。
6. 确认本轮可以结束后，提取长期记忆；如果写入了新记忆，再检查是否需要整理。
7. 结束本轮，等待下一次用户输入。

教程中 `if not tool_calls` 那段代码就在处理第 4～6 步。关键点是：模型暂时没有工具调用，还要先经过 `Stop` hook；hook 没有要求继续，才进入记忆提取和结束流程。

### 9. 自己写时，先抓住这几件事

不用一开始就把所有模型调用和异常处理堆进去，可以按下面的顺序理解和动手：

1. **先理解文件存取**：手动准备一条记忆，弄清正文、元数据和索引各自放什么。
2. **再打通召回**：让一次新请求能够选中记忆，并把正文交给模型，验证模型确实用到了它。
3. **再做自动提取**：完成回答后产生候选，检查作用范围、字段和重复情况，再写入磁盘。
4. **最后做整理**：处理重复记录，并考虑替换失败时如何恢复。

检查效果时，重点看 `.memory/` 的实际内容：是否写入了正确的信息、临时要求有没有被误存、新会话是否只读取相关记忆。模型口头说“我记住了”，不能单独证明保存成功。

### 10. 用三个问题检查自己是否理解

1. **记忆文件已经存在，模型为什么仍可能不知道？** 因为这次请求还没有加载对应正文，或者选择阶段没有选中它。
2. **既然保存了记忆，为什么还要 s08？** 因为长期记忆不会自动缩短当前会话不断增长的消息和工具输出，当前上下文仍然需要预算管理。
3. **本章最核心的三件事是什么？** 从对话中提取值得保存的信息；请求开始时选择相关记忆；积累后整理重复和过期内容。文件与索引为这三个过程提供持久存储。
